Carnet de décisions

La même mini-app sur les trois hébergeurs. Ici : un site statique, données dans un fichier.

Avantages

  • Gratuit, sans limite de durée
  • Rien à maintenir : pas de serveur
  • Les données sont versionnées dans git (historique de chaque modif)
  • Si GitHub ferme, on redéploie ailleurs en 5 minutes

Défauts

  • Le site est forcément public (même avec un compte payant)
  • Pas de vraie connexion : le « code » se vérifie dans ton navigateur
  • Lecture seule : personne ne peut voter ni ajouter depuis le site
  • Modifier les données = éditer un fichier sur GitHub

🔒 Entre le code

Comment ce code protège la page ? (spoiler : pas vraiment)

  1. Code en clair dans le HTML : clic droit → « Inspecter », et on le lit directement. Zéro protection.
  2. Code haché (ce qu'on fait ici) : la page ne contient que l'empreinte SHA-256 du code, f6563999cf206aa7c0113c3378785452f0950c37bf22742c5b8cf79ac3d2e2fb. On ne peut pas « inverser » un hash… mais avec 4 chiffres il n'y a que 10 000 possibilités : on les essaie toutes en une fraction de seconde.
  3. Et de toute façon : le hash protège la porte, pas le contenu. Les données sont dans data.json, lisible par n'importe qui, comme tout le repo GitHub.

Conclusion : sur GitHub Pages, tout est public. Parfait pour une vitrine ou une démo, jamais pour du confidentiel. Pour une vraie connexion, il faut un serveur qui vérifie le mot de passe — voir les versions Vercel et Raspberry.
